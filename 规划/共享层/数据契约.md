# 数据契约 —— 统一事件 Schema

> **契约版本：v0.2（草案）**
> 这是整个平台的地基，**独立版本化**：每次字段增删改都升版本号，并同步盖到每条记录的 `schema_version` 字段上。库里混存多版数据时据此解析。
> 注意：本「契约版本」与平台代码 / Git 版本是两回事，前者描述「数据长什么样」，后者描述「软件是哪一版」。
> 本版相对 v0.1 的变更：`user_id`/`team_id` 改为「门户注入，否则匿名」；`input_content`/`output_content` 从 LLM 专属移为通用选填（理由见 [决策记录](../../PROJECT_PLAN.md) #18、#20）。

每一次工具使用 = 一条记录。字段分三圈。

---

## 圈一：公共字段（硬性必填，任何工具都得给）

| 字段 | 类型 | 说明 |
|---|---|---|
| `record_id` | UUID | 记录唯一 ID（客户端生成，用于异步上报的幂等去重） |
| `schema_version` | string | **本条记录遵循的数据契约版本**。盖在每条记录上，库里混存多版数据时据此解析；与代码/Git 版本是两回事 |
| `tool_id` | string | 哪个工具（**由平台统一分配固定 ID**，工具方用这个 ID 对接，见 [工具注册表](工具注册表.md)） |
| `conversation_id` | string | **会话/任务 ID**：把同属「用户眼里一次使用」的多次调用串起来。**何为「一次使用」由工具按触发点自定义**（如点击「整体导出」即一次；一次使用内调了多个 API 就用同一 ID 串起）。最小记录单位是一次 API 调用，分析层按本字段聚合到「一次使用」。单次调用即一次使用的工具，本字段与 record_id 一一对应即可 |
| `start_time` | timestamp | 调用开始时间（统一 UTC） |
| `end_time` | timestamp | 调用结束时间（统一 UTC） |
| `duration_ms` | integer | 耗时（毫秒），建议采集端测量，避免跨机时钟偏差 |
| `status` | enum | success / failed / timeout |
| `ingested_at` | timestamp | 入库时间（服务端写入，区别于事件时间，便于处理晚到/异步数据） |

---

## 圈二：LLM 专属字段（调大模型的工具填，普通工具留 NULL）

| 字段 | 类型 | 说明 |
|---|---|---|
| `model` | string | 模型名 |
| `prompt_tokens` | integer | 输入 token（**归一化字段**，见下方说明） |
| `completion_tokens` | integer | 输出 token（归一化字段） |
| `total_tokens` | integer | 总 token（无则采集端 = 输入 + 输出 自行补齐） |
| `cost` | decimal | 本次成本（可空） |
| `cost_source` | enum | **成本来源**：`source`（源头直接返回，如异步任务的 `cost`）/ `computed`（分析层按价表算）。区分「事实」与「算出来的值」 |

> **Token 归一化（必读）**：不同接口/中转站的 token 字段名不统一。以 APIMart 为例——OpenAI 兼容接口返回 `usage.prompt_tokens / completion_tokens / total_tokens`；Claude Messages 接口只返回 `usage.input_tokens / output_tokens`（无 total）。**采集端负责把各家原始字段映射进上面这套统一字段**（Claude 的 input→prompt、output→completion、total 自补）。我们只定统一目标字段，怎么映射由采集端/工具方按契约完成。
>
> **缓存/推理 token**：目前对接的中转站（APIMart）不返回缓存命中、推理 token 的拆分，故**不单设列**；若将来某供应商返回此类明细，塞进 `metadata` 即可，不动主表。
>
> **关于价格→金额换算**：本阶段以 **token 计数准确** 为主，token→金额的换算后置。真正要把成本显示成「钱」时，需要一张**带生效时间的价格表**（每个 model 的价格带 effective_from/effective_to），否则重算历史成本会用错价。此表结构留待后续，不在本轮。

## 圈三 + 弹性选填

| 字段 | 类型 | 说明 |
|---|---|---|
| `user_id` | string | 使用者。**门户注入**：从平台入口打开工具时由平台注入真实使用者；无法归属到人时（绕过入口 / 黑盒工具）记为**匿名**。来源见 [架构-入口门户与账号体系](../总则/架构与原则.md) |
| `team_id` | string | 所属团队（随 `user_id` 解析；无法归属时同为匿名 / 空） |
| `result_quality` | float/enum | 结果质量信号（弹性选填，如用户点赞/采纳） |
| `adopted` | boolean | 结果是否被采纳（弹性选填，ROI 的关键输入） |
| `input_content` | text | 输入原文（**通用选填**：任何工具都可记，不限大模型；受敏感策略约束，见下文） |
| `output_content` | text | 输出原文（通用选填；受敏感策略约束） |
| `metadata` | JSONB | **自由口袋**：工具特异数据任意塞键值对，加字段不改主表 |

> **必填 vs 选填的意义**：圈一是入场券，给不出不许接；质量 / 采纳 / 输入输出内容是弹性选填，有就让分析多算几个维度。`user_id` 不做成「硬必填」——走门户的注入真人、绕过的记匿名，**始终不阻断入库**（不把工具挡在门外），又尽量认到人。绝不能把选填设成会拒收的必填。

> **ROI 的「产出/价值」**：分母（cost）已有；分子（产出/价值）工具自身通常产生不了，需另设反馈信号（人工打分 / 采纳率 / 业务回填）。用 `result_quality`、`adopted` 占位，具体用什么信号代表产出待定。

## 敏感内容策略（待人工确认）

`input_content` / `output_content` 是否存储、存全文还是摘要、**谁能在看板上查看这些原文（读取侧权限控制）**，按工具分级配置。

- 本平台**不做写入侧鉴权**：内部局域网工具发来的是真实使用数据，`tool_id` 由平台统一分配，「这条谁发的」靠分配的固定 ID 解决，恶意伪造不在威胁模型内。真正要管的是**读取侧**——谁能看含提示词/生成结果的原文。
- **留存策略**（原文存多久、是否到期转摘要/删除）后续随公司服务器部署再定，本轮不做，仅在此留位。
- 这一节整体一开始不定，后面极难补；脚手架中标注「待定，需人工确认」。
