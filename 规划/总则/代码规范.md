# 代码规范与工程纪律

> 专治：越写越乱、互相冲突、越写越大、修改残留、AI 不敢删。
> **核心思想：文档定方向，机器闸门执行。** 规范靠人自觉守不住，真正拦住「乱/残留/冲突」的是提交时报红的工具。两者都要。

---

## 一、技术栈（已锁定）

| 部分 | 选型 |
|---|---|
| 后端：接入 API / 分析层 | **Python 3.11+ + FastAPI** |
| 数据校验 / 模型 | **Pydantic v2**，**从 `shared/schema/event.schema.json` 代码生成**，不手写字段 |
| 数据库 | PostgreSQL（metadata = JSONB） |
| 参考 SDK | Python（匹配内部工具）；若某工具是别的语言，再单独提供对应语言 SDK |
| 转发服务 relay | 默认 Python（httpx + SSE）；若流式代理嫌费劲，**可单独用 Node 实现这一个组件**（它本就被设计成隔离可替换） |
| 前端（两个） | **React + Vite + TypeScript**：使用端门户（`apps/user-portal`）与数据端看板（`apps/admin-dashboard`）同栈 |
| 包管理 | 后端 `uv`；前端 `pnpm` |

> 换栈属于重大决策，要在 [PROJECT_PLAN](../../PROJECT_PLAN.md) 决策记录立项，不在代码里随手换。

---

## 二、单向依赖（防「互相冲突」的骨架）

依赖只能自下而上单向流，**禁止反向或跨层乱引**；最上层是两个并列前端，都只依赖下层、互不调用：

```
采集(collection: sdk/relay) → 接入(ingestion) → 存储(storage) → 分析(analytics) → 展示(apps: user-portal / admin-dashboard)
```

- 每层是独立的包/目录，有明确对外接口。
- 下层不许 import 上层；分析层不许碰采集层；**两个前端互不 import**。
- 跨层只通过「统一事件记录」这一个数据契约相连，不靠互相调用内部函数。
- 用工具固化：`import-linter`（Python）声明分层契约，违规即 CI 报红。

---

## 三、Schema 是唯一源（防「改一处漏四处」的冲突）

`shared/schema/event.schema.json` 是数据契约的唯一定义。各层**绝不手写一遍字段**：

- 后端模型：`datamodel-code-generator` 从 JSON Schema 生成 Pydantic 模型。
- 前端类型：`json-schema-to-typescript` 生成 TS 类型。
- 改字段 → 只改 JSON Schema → 重新生成 → 各层自动跟上。
- **生成出来的文件禁止手改**，文件头标注「自动生成，勿手改」；改了下次生成就被覆盖。

这一条直接消灭「字段定义散落在接入/存储/分析/前端四处、总有一处漏改导致冲突」。

---

## 四、删，不许注释掉（正面对治 AI 残留）

1. **删除就是删除**：废弃的代码直接删，**不许注释掉留着**、不许 `if False:`、不许 `# 旧版本保留`。历史归 git 管，不归注释管。
2. **禁止残留文件**：不许 `xxx_old.py`、`xxx_v2.py`、`xxx_copy.py`、`xxx_bak`。新版就地替换旧版（同「重构不打补丁」）。
3. **死代码必须清**：没有任何地方引用的函数/变量/文件，删掉。靠工具找出来（见 §5），不靠肉眼。
4. **AI 协作硬规矩**：改一个功能时，**旧实现要么删除、要么改写，绝不与新实现并存**。「不敢删就留着」是被禁止的——拿不准是否还在用，用死代码检测器确认，而不是默认保留。

---

## 五、机器闸门（CI + pre-commit，任一不过不许合并）

把纪律交给工具，每次提交自动执行：

| 关卡 | Python | 前端 TS | 治什么 |
|---|---|---|---|
| 格式化 | `ruff format` | `prettier` | 越写越乱 |
| Lint（含未用 import） | `ruff check` | `eslint` | 乱、小残留 |
| 类型检查 | `mypy --strict` | `tsc --noEmit` | 隐蔽冲突 |
| **死代码扫描** | `vulture` | `knip` / `ts-prune` | **残留、AI 不敢删** |
| 分层依赖 | `import-linter` | eslint import 规则 | 互相冲突 |
| 测试 + 覆盖率 | `pytest` + `coverage` | `vitest` | 改坏不自知 |

- 用 `pre-commit` 框架在本地提交前先跑一遍，CI 再把同一套跑一遍兜底。
- **死代码扫描红了不许「加忽略」糊弄**——除非有明确理由并写注释说明，否则就是该删。
- **闸门强度按阶段校准（保留早期灵活性）**：原型 / spike 分支上闸门放松——能跑、删残留即可，不必跟 `mypy --strict`、高覆盖率较劲；**合入主干前**才拧到全严格。别让探索期被类型检查拖慢。强度档位写进配置，由分支/阶段决定。

---

## 六、分析层写成纯函数（呼应原则二「计算后置」）

- 所有「成本/ROI/采纳率/质量」算式 = **输入原始事件、输出结果的纯函数**，不带副作用、不读全局状态。
- 因此**必须有单元测试**：给定一批事件，断言算出的指标。换算式先改测试。
- 算式变更不回填、不改历史原始数据——重算即可（这是「计算后置」能成立的前提）。

---

## 七、其他硬约束

- **配置/密钥不进代码**：中转站地址、API Key、DB 口令、AI 推荐用的 LLM 地址/Key 全走环境变量/配置文件，代码里零硬编码（呼应交接命令）。
- **文件/函数体量是信号不是红线**：单文件持续变大、单函数过长 → 是该拆分的信号，停下来拆，别继续堆。
- **一次提交只做一件事**：功能、重构、格式化分开提交，方便 review 和回溯。
- **不提前造抽象（YAGNI）**：没有第二个使用方就不抽公共层；但出现重复第三次时必须抽，别复制粘贴。

---

## 八、这些是默认，不是教条（明确保留灵活性）

项目尚处早期，本规范**全部是可改的默认值，不是焊死的命令**：

- 任何一条（含技术栈）都能改，走 [PROJECT_PLAN](../../PROJECT_PLAN.md) 决策记录立项即可——记下「原 X 改为 Y，因为 Z」，正文随之更新。
- 之所以现在就立约束，是因为它们大多是**解耦型**（规定各部分怎么连），让你以后能**一块一块地改而不牵连全局**；真正杀灵活性的是没约束导致的耦合和残留，不是约束本身。
- 唯一带单向门性质的是「锁语言」，但分层隔离 + 语言无关的数据契约让它**可逐层替换**、数据资产不受损，并非一次性赌注。
- 变化是预期内的：schema 用 `schema_version` 演进、metadata 当新数据的活门、分析维度随加随用——这套文档本就是为「会变」设计的。
