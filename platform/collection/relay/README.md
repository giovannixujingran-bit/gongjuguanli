## 一、定位（先认清边界）

relay 是给**不便改代码、又给不全数据**的工具准备的**兜底**采集通道——包括开源自部署（如 OpenClaw：代码可改但不想 fork 维护）与纯黑盒 SaaS（根本改不了）。判定看「能否/愿否改代码」而非工具是否开源。三条红线：

- **兜底，不是必经总闸**：能改代码的工具一律走工具自报（SDK / 自行上报）主路，**不强制走 relay**（呼应架构原则、决策 #19）。
- **采集点在自控层**：relay 是平台自建组件，采集逻辑写在它身上，**绝不写在随时会换的中转站上**（核心原则 3）。换中转站只改 relay 的一处配置。
- **最终落同一张表**：relay 采到的数据按统一 schema 走 `POST /events` 入库，和工具自报**同一个入库口径**，不另开落库路径。数据最粗时 `data_level = minimal`。

---

## 二、两种形态（确认采「两者都要」：A 为主路，B 为兜底）

### 形态 A —— 透明反向代理（主路）

工具把 LLM 接口的 `base_url` 改成指向 relay；relay 把请求**原样转发**给真实中转站，拿到响应后**旁路**抽取 token / 耗时 / status，构造一条 `UsageEvent` 发给 `/events`，再把响应原样返回给工具。工具侧只改一个地址，无感。

```
工具 --(base_url=relay)--> relay --(原样转发)--> 真实中转站
                            │
                            └─(旁路)→ 抽取 usage → POST /events → usage_event
```

要点：
- **流式（SSE）**：代理需透传 SSE 流给工具；usage 通常在流末尾才齐（OpenAI 兼容需上游开 `stream_options.include_usage`），relay 在**流结束后**再据末尾 usage 记完整记录（呼应接入契约「流式必须开 usage、流结束后再记」）。
- **失败 / 超时**：上游 4xx/5xx/超时也要记一条（`status=failed|timeout`）——这正是「哪个中转站不稳」的关键数据。
- **token 归一化**：直接复用 `collection.sdk` 的 `normalize_token_usage`（OpenAI / Claude 映射），不重写一套。

### 形态 B —— 旁路记录接口（兜底的兜底）

对连 `base_url` 都改不了、但能在某处拿到原始响应的工具：relay 暴露一个**记录接口**，工具 / 其包装层把拿到的原始 provider 响应 POST 过来，relay 归一化后落库。不转发请求，只记录。

要点：
- 适合「能在调用后处拿到响应、但没法把流量路由过 relay」的场景。
- 仍复用同一套归一化 + `/events` 入库。

## 三、统一字段约定（两种形态共用）

| 字段 | relay 怎么填 |
|---|---|
| `tool_id` | 按**独立 key** 或**转发路由**区分到工具；映射关系（key/路由 → tool_id）由配置提供 |
| `user_id` | 黑盒通常拿不到人 → `anonymous`；若上游透传了可信身份则带上 |
| `entry_source`（metadata） | `unknown`（黑盒）；relay 代采的可标 `relay` 以便区分来源 |
| 圈二 token | 能抽就抽（归一化后填）；异步任务两段式时 token 留 NULL、成本走源头 `cost`（`cost_source=source`） |
| `record_id` | relay 生成，保证幂等去重 |

## 四、技术栈与配置

- **技术栈**：默认 Python（httpx + SSE）；若流式代理用 Python 实现成本过高，可**单独**用 Node 实现 relay 这一个组件（决策 #13，relay 是隔离可替换组件，单拆不影响主干）。
- **配置全走环境变量**：真实中转站地址、key → tool_id 映射、`/events` 地址等一律 `.env`，**代码与镜像零硬编码**。
