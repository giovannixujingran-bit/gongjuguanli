# 架构与原则

> 稳定层：项目是什么、为什么这么设计。几乎不随实现变动。
> 配套文档见 [总纲](../../PROJECT_PLAN.md)。

---

## 一、项目是什么

一个部署在**公司局域网内**的统一中枢平台，把公司里各种工具（自己写的、开源自部署的、买来的黑盒工具）的**每一次使用**汇总记录下来，并在这些数据之上做分析。

平台由**两个前端 + 一套共享后端**组成（按使用端 / 数据端 / 共享层三个面向划分）：

- **使用端 · 使用者门户**：面向普通使用者的入口。分类卡片式列出可用工具、按偏好/使用情况排序、AI 按需求推荐工具；使用者从这里登录并打开工具。详见 [使用端-工具门户](portal.md)。
- **数据端 · 后台分析台**：面向管理者的看板。明细查询 + 四类分析 + 接入与账号管理。
- **共享后端（共享层）**：采集、存储、分析、账号体系、[工具注册表](registry.md)——两个前端共用的同一套数据与服务。

两个前端共享同一套账号、工具注册表与事件数据；用户身份来自同一套账号体系。门户在「打开工具」时可以注入身份；不从门户进入的工具，也可以通过平台 Auth API / SDK 使用同一套账号识别用户（详见下文「入口门户与账号体系」一节）。

要做出的四类分析结论：

1. 成本与 token 消耗
2. 效率与投入产出（ROI）
3. 使用率与采纳情况
4. 结果质量评估

## 二、三条不可动摇的核心原则

整套设计的骨架。任何实现决策若与这三条冲突，以这三条为准。

1. **数据契约统一，接入方式可变。**
   不强求工具长得一样，只强求它们最终落库的那条记录格式一样（统一 schema）。这是地基——格式统一，分析层才能跨工具横向比较。

2. **采集端只记原始事实，计算一律后置。**
   采集端只诚实记录「发生了什么」（消耗多少、用了多久、成功与否、输入输出是什么）。所有「效率 / ROI / 单位成本」这类**会变的算式**，全部放到分析层去算。会变的算法与不变的事实分开存放，换指标时才不必返工。

3. **采集点放在可长期掌控的那一层，绝不绑定会被替换的外部依赖。**
   第三方 API 中转站是随时会更换的外部供应商，采集逻辑绝不写在它身上。采集点放在「自己的工具 SDK」或「自建的本地转发服务」里。换中转站时，只改一处配置，数据主干不受影响。

## 三、整体架构

数据自下而上流经五层；最上层的展示层是**两个并列的前端**，共用下面同一套后端：

```
┌────────────────────────────────────────────────────────────────┐
│  5. 展示层（两个前端，共用下面同一套后端）                      │
│     · 使用端 · 使用者门户：分类卡片 · 排序 · AI 推荐 · 登录入口  │
│     · 数据端 · 后台分析台：明细查询 · 四类看板 · 接入/账号管理   │
├────────────────────────────────────────────────────────────────┤
│  4. 分析层  Analytics                                           │
│     成本 · ROI · 采纳率 · 质量（所有算式在此，可随时改）        │
├────────────────────────────────────────────────────────────────┤
│  3. 存储层  Storage（共享数据）                                 │
│     统一事件表 · 工具注册表 · 用户账号表                        │
│     PostgreSQL（metadata 用 JSONB）                             │
├────────────────────────────────────────────────────────────────┤
│  2. 接入层  Ingestion                                           │
│     统一上报 API（接收一条流水）+ 进入即自动校验契约            │
├────────────────────────────────────────────────────────────────┤
│  1. 采集层  Collection（三种手段，落同一格式）                  │
│     a) 工具自报 —— 触发点直接上报（SDK 为便捷封装，主路）       │
│     b) 本地转发服务 —— OpenClaw / 黑盒工具的请求改指向它        │
│     c) 独立 API Key —— 黑盒工具按 key 区分到「哪个工具」        │
└────────────────────────────────────────────────────────────────┘
```

**两个前端只通过共享后端的数据相连，不互相调用**：使用端门户从[工具注册表](registry.md)读「展示信息」、从事件表读「使用情况」做排序（跨端只读）；数据端看板从分析层读四类结论。各前端自身不存业务数据。

全部组件部署在局域网内，相互直接互通；无需考虑跨网穿透。中心平台可选择基于开源可观测系统（Langfuse / Helicone 私有化部署）二次开发，或完全自建——本计划按自建脚手架组织，但保留替换空间。

## 四、工具分三类，采集方式不同，最终落同一张表

| 类别 | 例子 | 采集手段 | 能拿到的数据粒度 |
|---|---|---|---|
| 自写 / 可改代码 | 公司内部脚本、服务 | **工具自报**：在调用或按钮**触发点**把数据报给平台统一上报 API（参考 SDK 是这一步的便捷封装，工具也可自行实现上报） | 最全：token + 工具 + 用户 + 团队 + 结果 |
| 开源自部署 | OpenClaw | 改不动代码但能改地址：把接口地址（base URL）指向本地转发服务，由平台旁路代采 | token + 工具；用户粒度取决于它透传什么 |
| 纯黑盒现成 | 买来的闭源 SaaS / 软件 | 独立 API Key 区分到工具，或走转发服务兜底 | 通常只到「哪个工具」，拿不到「哪个人」 |

**手段有主次**：能改代码的工具一律走**自报**（最直接、数据最全，是主路）；转发服务与独立 key 只是给「改不了代码的黑盒工具」兜底，**不是所有流量的必经总闸**。无论哪种，采集点都放在自己掌控的工具 / 转发服务里，不写在随时会换的中转站上（与核心原则 3 一致）。

**不调大模型的工具也能接**：它没有 token / 成本，圈二留 NULL，只记圈一（次数、耗时、status）＋（可选）输入输出内容 / metadata。何为「一次使用」由工具按触发点自定义（如点击「整体导出」即一次）。

**关键设计：无论哪种手段，最终都按同一 schema 落库。** 差异由 schema 的「弹性选填字段」和「metadata 自由区」吸收。具体字段见 [数据契约](schema.md)。

## 五、入口门户与账号体系

平台不只是被动汇总数据，它同时提供一套**统一用户系统**。用户身份不只服务于使用端门户，也可以被外部工具通过 Auth API / SDK 复用。

入口分两类：

| 入口 | 含义 | 身份识别 |
|---|---|---|
| `portal` | 用户先登录平台，再从使用端门户打开工具 | 门户签发短期 `launch_token` / 会话，工具校验后上报可信身份 |
| `direct` | 用户绕过门户，直接打开工具本身 | 工具接入平台 Auth API / SDK，用户用同一套账号登录后上报可信身份 |
| `unknown` | 工具无法接入统一身份，或来源无法识别 | 记录照收，`user_id = anonymous` |

- **门户定位**：使用者可以先登录平台，再从平台入口打开各工具。平台在「打开工具」时把当前使用者的身份通过短期 token 注入过去，工具上报时带回可信身份。门户的功能细节见 [使用端-工具门户](portal.md)。
- **direct 入口**：不强制所有使用都走门户；能改代码的工具可以接入平台 Auth API / SDK。用户即使直接打开工具，也能用平台账号登录并被识别为同一个 `user_id`。
- **匿名兜底**：接不进统一身份的工具，记录照收，但使用者记为**匿名**。即「能认就记真人，认不出就记匿名」，既尽量认人、又不阻断入库。
- **入口来源先入 metadata**：Phase 2 先把 `entry_source = portal | direct | unknown`、`auth_method = launch_token | session_token | none` 放进 `metadata`。等 SDK、demo 工具和低风险真实工具验证稳定后，再决定是否升 schema v0.3，把入口来源转成正式字段。
- **账号体系（用户账号表）**：一人一账号，管理员发放初始账号密码，密码由用户自行修改、**库内存哈希不存明文**（内部局域网，无需更重的安全机制，呼应「不做写入侧鉴权」的威胁模型）。此表是 `user_id` 的来源，也是将来**读取侧权限**（谁登录后能看什么、能否看原文）按人分级的挂靠点——读取侧细则仍**待定，需人工确认**。

> **两张表别混**：用户账号表管「人」（`user_id`），[工具注册表](registry.md) 管「工具」（`tool_id`）。一条记录 = 哪个人用了哪个工具，两表各管一半。
