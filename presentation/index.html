定位与问题

它是什么，要解决什么

定位
部署在公司局域网内的统一中枢，把各类工具（自写 / 开源自部署 / 黑盒）的每一次使用汇总记录，并在其上做分析。
要解决的问题
公司内部工具持续增多，但每个工具的使用频次、用户采纳、资源成本与产出质量缺乏统一、可比的度量——管理者难以判断哪些工具值得投入、哪些在闲置。
怎么组成
两个前端（使用端·使用者门户 / 数据端·后台分析台）＋ 一套共享后端（采集 / 存储 / 分析 / 账号 / 注册表）。
统一度量的四个维度
  1. 成本与 token 消耗
  2. 效率与投入产出 ROI
  3. 使用率与采纳情况
  4. 结果质量评估
核心设计原则

三条原则，决定了其余一切

这是整套设计的骨架。后面每个具体设计，都是这三条的落地——读到时会看到对应的回扣徽标。

原则 01

数据契约统一
接入方式可变

不强求工具长得一样，只强求它们最终落库的那条记录格式一样（统一 schema）。怎么接随工具，记录长什么样不容商量。

格式统一，分析层才能跨工具横向比较。
原则 02

先把事实记准
怎么算以后再说

记录时只老实存「死的事实」——这次用了多少、花了多久、成没成、问了啥答了啥。至于「单价多少钱、ROI 怎么算」这类会变的算法，先不算，等分析时再套公式。

哪天改了价格或算法，重算一遍就行，不用回头改历史数据。
原则 03

埋点放自己手里
不绑外部供应商

记录数据的那段代码，放在自己能掌控的东西里（自家工具的 SDK，或自建的转发服务），别写在随时可能更换的第三方中转站上。

哪天换了中转站，只改一处配置，已记的数据和逻辑都不受影响。

统一数据契约

放大看：那条记录长什么样

落实原则 01：数据契约统一，接入方式可变

工具千差万别，但落库的那条记录格式必须一样——这是全平台可比较的地基。字段分三圈。

圈一 · 公共必填

任何工具都得给

记录 ID · 工具 · 使用者 · 起止时间 · 耗时 · 成败状态。

入场券：给不出这些，不许接入。
圈二 · LLM 专属

调大模型的工具填

模型名 · 输入 / 输出 token · 成本（按统一字段归一化）。

不调模型的工具留空，不影响入库。
圈三 · 弹性选填

有就多算几个维度

输入 / 输出原文 · 质量 · 是否采纳 · metadata 自由字段。

新字段先进 metadata，按需要再晋升为列。
运行方式

这套东西，怎么跑起来

目标部署形态是 docker-compose，局域网内一键起。启动链路：

1docker-compose up一条命令，按清单一键起整套服务
2起 PostgreSQL数据库容器跑起来（此时还是空库）
3跑迁移建表按编号执行迁移脚本，把三张表建好/更新
4起接入 API后端起来，开始能收数据
5起两个前端门户 + 看板
6健康检查通过 ✓确认每个组件都活着、连得上
本机开发变体：当前开发机用「免安装 PostgreSQL + serve.ps1」——一条命令自动 起 PG → 真实探活 DB → 起接入 API → 探活 /health，连不上当场报错、不假装起好。

数据从哪来：三种采集手段

用哪种手段，取决于你对这个工具握有哪一级控制权——与它开源还是闭源无关。越往上数据越全，能走上面的就别用下面的：

能改它的
代码
工具自报（主路）
在调用 / 按钮触发点直接上报，SDK 是便捷封装，也可自行实现。
数据最全：token + 工具 + 用户 + 团队 + 结果
改不了 / 不想改代码，但能改
接口地址
本地转发服务
把 base URL 指向平台转发服务，旁路代采。不想 fork 的开源、可配 endpoint 的闭源都适用。
token + 工具（+ 原文）；缺用户 / 触发语义
连地址都改不了，但能定它用
哪把 key
独立 API Key
给每个工具发专属 key，供应商按 key 报量，凭 key 认出是哪个工具。
最粗：通常只到「哪个工具 + 总用量」

判定看控制权、不看出身：闭源工具只要暴露可配置 base URL，照样走转发；转发 / 独立 key 只是兜底，不是所有流量的必经总闸。

关键取舍

每个选择，都有「为什么」

决策我们的选择为什么
技术栈锁定 Python + FastAPI重心是数据分析与 LLM 埋点，Python 是主场
数据契约一份 schema 生成各层模型消灭「改一处漏四处」
写入侧鉴权内网不做，只认 tool_id威胁模型务实，绝不阻断入库
字段治理metadata 三层 ＋ 按信号晋升既灵活又不失控，长期可维护
转发服务隔离、可替换、非必经换中转站不动数据主干
库结构演进迁移执行器幂等管理「schema 可演进」真正落到库上
